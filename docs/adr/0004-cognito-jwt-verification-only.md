# ADR-0004: Cognito Hosted UI採用、バックエンドはJWT検証のみ

- Status: Accepted
- Date: 2026-07-18
- Updated: 2026-10-04

## Context

移植元の実装はX-User-Idヘッダの値でユーザーを識別しており、認証の仕組みがない。この値を書き換えれば誰にでもなりすませるため、社内利用であってもこのまま運用はできない。課題は、パスワード管理やトークン発行を自前で実装せずに、信頼できるユーザー識別をどう実現するかである。

## Decision

Cognito User PoolのHosted UIを利用し、Authorization Code + PKCEフローで認証する。FastAPIはアクセストークンのJWT検証とユーザー識別のみを行い、パスワード管理やJWT発行は実装しない。

ただし、ADR-0018によりバックエンドの責務を広げた。api-fnが認可コードの交換、トークンの更新と失効をCognitoとの間で行い、トークンをHttpOnly Cookieとして発行する。トークンを発行するのは引き続きCognitoであり、パスワードも扱わない。

採用理由は、認証情報の保管と発行をマネージドサービスへ委譲でき、招待制で登録する社内ユーザーの規模ではCognitoの無料枠内で運用できるためである。認証フローや画面遷移、ユーザー登録、トークン保存、ライブラリ選定などの詳細は[authorization.md](../authorization.md)に記載する。

## Consequences

メリット

- パスワード保管とトークン発行の実装および漏えいリスクをバックエンドから排除できる
- ユーザー識別が署名検証を通るため、ヘッダー偽装によるなりすましができない
- 想定ユーザー数ではCognitoの無料利用枠に収まる

デメリット・制約

- Hosted UIの画面デザインはカスタマイズの自由度が低い
- 認証仕様がCognitoに依存し、他基盤への移行コストが生じる

見直し条件

- 社外ユーザーへの提供や新たなIdP連携要件が生じた場合は、Cognitoの認証構成を見直す

## Alternatives

### X-User-Idヘッダの継続利用

実装コストはゼロだが、なりすましを防げない。認証基盤としての要件を満たさないため不採用とした。

### 認証の自前実装

FastAPI側でパスワード保管とJWT発行を実装する方式である。要件に合わせた自由度は最も高いが、認証情報の保護、パスワードリセット、トークン失効などの実装と運用リスクをすべて自前で負うことになる。セキュリティ上の利点がないため不採用とした。

### Auth0などの外部IDaaS

機能とドキュメントは充実しており、無料プランでも本システムのユーザー数は収容できる。しかしAWS外への依存が増え、IAMとは別にアカウント管理の系統を持つことになる。CognitoであればAWS上のリソースとしてCDKによるIaC管理に統一でき、要件も満たせる。
