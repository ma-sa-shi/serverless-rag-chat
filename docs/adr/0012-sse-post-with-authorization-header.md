# ADR-0012: チャットのSSEをPOSTで配信する

- Status: Accepted
- Date: 2026-08-06
- Updated: 2026-10-04

## Context

chat-fnは質問を受け取り、LangGraphのnodeごとのstate更新をSSEで配信する。このストリームをブラウザからどう受け取るかが課題である。

ブラウザ標準のEventSourceはGETのみを扱い、リクエストボディもリクエストヘッダーも設定できない。そのため、EventSourceを使う場合は質問をクエリ文字列で送ることになる。

質問は最大2000文字を受け付ける。日本語はUTF-8で1文字3バイトであり、パーセントエンコードすると9バイトへ膨らむ。そのため、クエリ文字列で送る場合、最長の質問はURLだけで18KB近くに達する。

## Decision

`POST /api/chats/stream`で質問をリクエストボディとして送る。クライアントはEventSourceを使わず、fetchのレスポンスボディを読み進めてSSEを自前で解析する。認証は他のAPIと同じく、Cookieで送られるアクセストークンで行う。

採用理由は次の2点である。

- 質問の長さがURLの制限を受けない
- 質問がURLに現れない。アクセスログや障害調査で共有する記録へ、質問の本文が平文で残る経路を持たない

当初はアクセストークンをAuthorizationヘッダーで送っており、EventSourceではトークンをURLへ載せるしかないことも、POSTを選んだ理由であった。ADR-0018でトークンをHttpOnly Cookieへ移したことでこの理由はなくなったが、上記の2点によりPOSTを維持する。

## Consequences

メリット

- 質問の長さがURLの制限を受けない
- SSEを配信するエンドポイントを、他のAPIと同じ認証・ルーティングの枠組みで扱える

デメリット・制約

- EventSourceの自動再接続と、Last-Event-IDによる再開を利用できない。ストリームが切れた場合は失敗として扱い、利用者が質問を送り直す
- ストリーム全体の上限は、API Gatewayの統合タイムアウトである300秒となる。Self-RAGの実行時間はこれに収まるため、切断は例外的な事象である
- SSEの解析をクライアントで実装する。fetchで呼ぶためaxiosのインターセプタを共有できず、アクセストークンの期限切れ時の更新と再送も個別に書く。イベントの境界とマルチバイト文字がチャンク境界で分割される場合も自前で扱う

ただし、再接続を放棄する代償は本システムでは限定的である。

- グラフはcheckpointerを持たず、中断した位置から再開できない。再接続してもグラフ全体が再実行され、LLMとRerankの呼び出しが再度課金される
- 永続化はdoneイベントの直前にまとめて行う。ストリームが切れた場合DynamoDBには何も残らないため、質問を送り直すことが唯一の復旧手段になる

見直し条件

- 途中再開を実装する場合は見直す。checkpointerの導入と、Last-Event-IDを受け付ける仕組みが前提になる

## Alternatives

### EventSourceとクエリ文字列による質問の受け渡し

EventSourceを使い、質問をクエリ文字列で送る案である。アクセストークンはCookieで自動送信されるため、URLには載らない。クライアントの実装量が小さく、自動再接続も備える。しかしcheckpointerを持たない本システムでは、再接続はグラフ全体の再実行にしかならず、利点として働かない。

一方で、最長の質問ではURLが18KB近くに達し、CloudFrontのURL長のクォータ8192バイトを超える。また、CloudFrontとAPI Gatewayのアクセスログは現時点で有効化していないものの、障害調査のために後から有効化しうる。有効化した時点から、すべての質問の本文がログに平文で記録される。そのため不採用とした。

### SSE解析ライブラリの導入

fetchでSSEを扱うライブラリを導入する案である。再接続やリトライを含む実装を任せられる。

しかし本システムが受け取るイベントは3種類に固定されており、再接続も上記のとおり利用しない。解析処理は60行程度に収まり、依存を1つ増やすほどの規模ではないため不採用とした。将来イベント種別が増えるか再接続が必要になった場合は再検討する。
