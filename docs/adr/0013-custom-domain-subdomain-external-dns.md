# ADR-0013: 独自ドメインはサブドメインで公開し、DNSをお名前.comに置く

- Status: Accepted
- Date: 2026-08-09

## Context

保有しているドメイン`business-efficiency.pro`でアプリケーションを公開する。ドメインはお名前.comで取得し、管理している。

これまではCloudFrontのデフォルトドメインである`dxxxxxxxxxxxxx.cloudfront.net`で配信してきた。しかし、この構成ではデプロイに手間がかかる。CognitoのコールバックURLとドキュメント保存用S3バケットのCORS許可オリジンにはCloudFrontのドメインが必要だが、DataStackからEdgeStackを参照すると循環参照になる。そのためドメインはコンテキスト`appDomain`で外から渡しており、初回はEdgeStackを構築してから、払い出されたドメイン名でDataStackを再デプロイしている。独自ドメインを使えば、この値がデプロイ前に決まる。

論点は、apexで公開するか、サブドメインで公開するかである。apexは`business-efficiency.pro`そのものを、サブドメインは`rag.business-efficiency.pro`のような形式を指す。

DNSの仕様上、apexにはCNAMEレコードを設定できない。そのためapexをCloudFrontへ向けるには、Route53のALIASレコード、エニーキャスト静的IPへのAレコード、ALIAS/ANAME相当の機能を持つDNSサービスへのネームサーバー移管のいずれかが必要になる。一方、お名前.comのDNSレコード設定はALIAS/ANAMEに対応していないため、今のDNSのままではapexをCloudFrontへ向けられない。

本システムは固定費を避ける方針で、インフラの固定費は月約$0.4に収まっている。apexで公開するために月額の固定費を払うかどうかが、判断の分かれ目になる。

## Decision

SPAの公開ドメインはサブドメインの`rag.business-efficiency.pro`とし、DNSはお名前.comのDNSレコード設定をそのまま使う。Route53のホストゾーンは作らない。

- CloudFrontの代替ドメイン名にサブドメインを設定する
- ACM証明書はus-east-1でDNS検証により発行し、検証用のCNAMEレコードをお名前.comに登録する
- サブドメインのCNAMEレコードをCloudFrontのディストリビューションドメインへ向ける
- apexは使わない

採用理由は次の3点である。

- 固定費が増えない。ACM証明書、CloudFrontの代替ドメイン名、お名前.comのDNSレコード設定はいずれも追加料金がかからない
- サブドメインは通常のCNAMEレコードで解決でき、DNSサービス独自の機能に頼らずに済む
- `appDomain`がデプロイ前に決まり、EdgeStackを構築してからDataStackを再デプロイする手順がなくなる

## Consequences

メリット

- 公開URLが自分のドメインになり、CloudFrontのデフォルトドメインを使わずに済む
- `appDomain`が固定値になり、初回デプロイを2回に分ける必要がなくなる

デメリット・制約

- apexではアクセスできない。ブラウザに`business-efficiency.pro`と入力しても表示されない
- ACM証明書はus-east-1で発行する必要がある。他のスタックとリージョンが異なるため、証明書用のスタックを分け、リージョンをまたいで参照することになる
- DNSレコードがCDKの管理外になる。証明書の検証用とサブドメイン用のCNAMEレコードはお名前.comのコントロールパネルで手動設定するため、手順を`cdk/README.md`に残す必要がある

見直し条件

- apexでの公開が必要になった場合は、CNAMEフラット化に対応したDNSへのネームサーバー移管か、Route53のホストゾーンとALIASレコードの導入を検討する

## Alternatives

### apex + Route53のALIASレコード

Route53にパブリックホストゾーンを作り、ALIASレコードでapexをCloudFrontへ向ける標準的な構成である。AWS内で完結するため、DNSレコードもCDKで管理できる。

しかし、ホストゾーンには月$0.50の固定費がかかる。使っても使わなくても課金される専有リソースであり、固定費を避ける方針がまさに排除している対象にあたる。システム全体の費用でも月$1〜2の構成で、ドメイン1つのためにこの固定費を払うほどの利点はないため、採用しない。

### apex + CloudFrontのエニーキャスト静的IP

2025年4月からapex向けのエニーキャスト静的IPが提供されており、Aレコードでapexを向けられる。ただし、IPリスト1つあたり月$3,000かかり、本システムの規模とは桁が違うため採用しない。

### ネームサーバーをCloudflareへ移してapexを使う

CloudflareのDNSは無料プランでもCNAMEフラット化に対応しており、固定費をかけずにapexをCloudFrontへ向けられる。

しかし、ドメインの取得先であるお名前.comとは別にDNSの管理先ができ、依存するサービスが1つ増える。apexでの公開が要件ではない今は移す理由がないため、採用しない。ただし、apexが必要になった場合の第一候補として残す。

### CloudFrontのデフォルトドメインのまま運用する

追加の作業も費用もかからない。しかし、初回デプロイを2回に分ける手順が残り続け、保有しているドメインも活かせない。独自ドメインの導入にかかる手間と費用は小さいため、採用しない。
