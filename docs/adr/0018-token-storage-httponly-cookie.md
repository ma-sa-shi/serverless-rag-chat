# ADR-0018: トークンをHttpOnly Cookieへ保存する

- Status: Accepted
- Date: 2026-10-04

## Context

ADR-0010では、SPAがCognitoから受け取ったアクセストークンとリフレッシュトークンをlocalStorageへ保存し、XSSによる窃取のリスクを受容した。緩和策の中心はCSPの`connect-src`による送信先の制限である。

しかしこの緩和策では、リフレッシュトークンの持ち出しを防ぎきれない。`connect-src`が制限するのはfetchやXHRの送信先であり、ページ遷移やリンクのURLにトークンを載せて外部へ送る経路は塞げない。リフレッシュトークンは30日間有効であるため、一度持ち出されると、攻撃者は自分の環境からアクセストークンを取得し続けられる。XSSの被害が、ページを開いている間の操作にとどまらず、最長30日間のなりすましへ広がる。

移行先の検討では、次の前提が制約になる。

- SPAとAPIはCloudFrontの同一オリジンで配信している
- API GatewayのCognitoオーソライザは、リクエストヘッダーに載ったトークンしか検証できない
- バックエンドの責務はJWTの検証のみであり、Cognitoとトークンをやり取りする処理を持たない

## Decision

トークンをHttpOnly Cookieへ保存する。認可コードの交換、トークンの更新と失効をSPAからapi-fnへ移し、api-fnがCookieを発行する。これにより、ADR-0004で定めたバックエンドの責務を、JWTの検証からCognitoとのトークンのやり取りまで広げる。ただし、パスワードの取り扱いとトークンの発行は引き続き行わない。

採用理由は、JavaScriptからトークンを読み取れなくなることである。XSSが起きても被害はページを開いている間の操作に限られ、リフレッシュトークンは持ち出されない。

### Cookieの構成

トークンはサーバー側にセッションを持たず、Cookieへそのまま格納する。セッションストアとその有効期限の管理が不要になり、Cognitoのトークンはそれぞれ4KBのCookieの上限に収まる。

| Cookie | 値 | Path | SameSite | 有効期限 |
|--------|----|------|----------|---------|
| `__Host-access_token` | アクセストークン | `/` | Strict | 1時間 |
| `__Secure-refresh_token` | リフレッシュトークン | `/api/auth` | Strict | 30日 |
| `__Secure-auth_tx` | state、code_verifier、サインイン後の遷移先 | `/api/auth` | Lax | 10分 |

すべてにHttpOnlyとSecureを付け、Domainは指定しない。リフレッシュトークンはPathを`/api/auth`に絞り、更新とサインアウト以外のリクエストには載せない。`__Secure-auth_tx`だけをLaxにするのは、Cognitoから戻るコールバックが別サイトからの遷移であり、Strictでは送信されないためである。

### 認証の流れ

- `GET /api/auth/login`がPKCEのcode_verifierとstateを生成して`__Secure-auth_tx`へ保存し、Hosted UIへリダイレクトする
- `GET /api/auth/callback`がstateを照合して認可コードを交換し、Cookieを発行して元の画面へ戻す。IDトークンはこの時点で検証し、表示名とメールアドレスをDynamoDBへ同期した後に破棄する。SPAは利用者の情報を`GET /api/users/me`で取得する
- アクセストークンの期限が切れると、APIは401を返す。SPAは`POST /api/auth/refresh`を1回呼んでから元のリクエストを再送する。更新にも失敗した場合、画面の表示時であればサインインへ遷移させ、操作中であれば再読み込みを促す。入力中の質問を失わせないためである
- `POST /api/auth/logout`がリフレッシュトークンを失効させてCookieを削除し、Cognitoのログアウト先のURLを返す

リダイレクト先のURLは、設定したアプリのオリジンから組み立てる。CloudFrontがオリジンへ渡すHostはAPI Gatewayのドメインであり、Hostから組み立てると利用者をAPI Gatewayへ直接誘導してしまう。

Cognitoのアプリクライアントは既存のパブリッククライアントを使い、PKCEはapi-fnが行う。client_idが変わらないため、オーソライザとFastAPIのJWT検証は設定を変えずに済む。

### オーソライザへのトークンの受け渡し

`/api/*`のビヘイビアにCloudFront Functionを置き、`__Host-access_token`の値を`Authorization`ヘッダーへ写す。リクエストが`Authorization`ヘッダーを持つ場合は書き換えない。オーソライザはこのヘッダーを検証するため、Lambdaの起動前に無効なトークンを拒否する仕組みはそのまま残る。

FastAPIは`Authorization`ヘッダーを優先して読み、無い場合はCookieを読む。CloudFrontを経由しないローカル開発ではCookieから直接読むことになり、本番と同じSPAの実装で動く。

`/api/auth/*`にはオーソライザを付けない。期限切れのアクセストークンしか持たない状態で更新を呼ぶ必要があるためである。

### CSRF対策

アクセストークンとリフレッシュトークンのCookieをSameSite=Strictとし、別サイトから始まるリクエストには送信させない。加えて、POST・PUT・PATCH・DELETEのリクエストが`Origin`ヘッダーを持ち、その値がアプリのオリジンと異なる場合、FastAPIが403を返す。ブラウザは更新系のリクエストへ`Origin`を必ず付けるため、`Origin`を持たないのはブラウザ以外のクライアントであり、CSRFの経路にならない。サインインの開始とコールバックはstateの照合で、別人のアカウントへサインインさせる攻撃を防ぐ。

チャットのSSEも同じCookieで認証する。質問をPOSTのボディで送る方式は変えない。

### 既存セッションの扱い

localStorageのトークンはCookieへ引き継がず、切り替え時に全利用者へ再サインインを求める。引き継ぐにはJavaScriptからリフレッシュトークンをバックエンドへ送る経路が必要になり、この決定で取り除く露出をあえて作ることになるためである。切り替え直後に全ユーザーへグローバルサインアウトを実行し、localStorageに残ったリフレッシュトークンを失効させる。

## Consequences

メリット

- XSSが起きてもトークンを読み取られず、被害はページを開いている間の操作に限られる
- SPAがCognitoと直接通信しなくなる。`oidc-client-ts`と`react-oidc-context`を除き、CSPの`connect-src`からCognitoのオリジンを外せる
- プロフィールの同期がサインイン処理の中で完結し、SPAから同期のリクエストを送る必要がなくなる
- 複数タブとリロードでセッションを維持できる点は変わらない。Cookieはタブ間で共有されるため、1つのタブで更新したトークンを他のタブもそのまま使える

デメリット・制約

- バックエンドの実装と責務が増える。サインイン、コールバック、更新、サインアウトの4つのエンドポイントとCSRF対策を自前で持つ
- `/api/auth/*`は未認証のリクエストでもapi-fnを起動する。上限はステージのスロットリングのみである
- 認証の経路にCloudFront Functionが加わる。課金は呼び出し回数に応じた従量であり、固定費は生じない
- HttpOnlyで防げるのはトークンの持ち出しまでである。XSSのスクリプトは、ページを開いている間ならCookie付きのリクエストでAPIを操作できる。そのため、CSPによる緩和策は引き続き必要である
- ローカル開発は`http://localhost`で動かすため、Secure属性の付いたCookieを`localhost`で保存できるブラウザに限られる
- 切り替え時に、全利用者が1回サインインし直す必要がある

見直し条件

- モバイルアプリなど、別オリジンや非ブラウザのクライアントからAPIを呼ぶ必要が生じた場合は、トークンの受け渡し方式を再検討する
- Cognitoのリフレッシュトークンのローテーションを有効にする場合は、複数タブからの同時更新の扱いを再検討する

## Alternatives

### localStorageへの保存を維持する

実装の変更が不要で、バックエンドの責務も広がらない。しかしContextに記載したとおり、リフレッシュトークンの持ち出しを防げず、XSSの被害が最長30日間のなりすましへ広がる。この影響を受容しないため不採用とした。

### サーバー側セッションと不透明なセッションID

トークンをDynamoDBに保存し、Cookieにはランダムなセッションの識別子だけを載せる方式である。サーバー側でセッションを即座に無効化できる。

しかし、セッションのアイテムとその有効期限を管理する必要があり、すべてのリクエストでDynamoDBの読み出しが加わる。さらに、Cognitoオーソライザはセッションの識別子を検証できない。そのため、Lambdaオーソライザを新たに設けるか、Lambda起動前の拒否を諦めることになる。トークンを直接Cookieへ入れる方式で要件を満たせるため不採用とした。

### CookieをLambdaオーソライザで検証する

Lambdaオーソライザであれば、CloudFront Functionを使わずにCookieからトークンを読み取れる。しかし、JWKSの取得と署名検証をオーソライザ用に実装し直すことになり、Cognitoオーソライザが標準で提供する機能を再実装することになる。オーソライザのキャッシュが効かないリクエストではLambdaの呼び出しも増えるため不採用とした。

### クライアントシークレット付きのアプリクライアントを新設する

リフレッシュトークンが漏えいしても、シークレットを持たない第三者はトークンを更新できない。しかしリフレッシュトークンはHttpOnly Cookieに入り、JavaScriptからは読めない。そのため、シークレットで防げる経路はほとんど残らない。一方で、シークレットの保管とローテーションの運用が増え、client_idの変更に合わせてオーソライザとJWT検証の設定も切り替える必要がある。得られる保護に対して負担が大きいため不採用とした。
