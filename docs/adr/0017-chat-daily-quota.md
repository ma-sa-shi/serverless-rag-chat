# ADR-0017: チャットの利用量を回数制のチケットで制限する

- Status: Accepted
- Date: 2026-08-30
- Updated: 2026-09-12

## Context

固定費を避ける構成のなかで、Bedrockの推論費用だけが利用量に比例して増え、上限を持たない。1人のユーザーがチャットを送り続けるだけで月額費用が読めなくなる。

API Gatewayのステージには20リクエスト/秒、バースト40のスロットリングを設定しているが、これは瞬間的な流量を抑えるものであり、累積の呼び出し回数には効かない。

上限の単位を決めるため、6件のチャットで利用量を実測した。1チャットあたりの平均はLLMの入力5,514トークン、出力485トークン、Embedding 3.7回、Rerank 1回である。ap-northeast-1のオンデマンド単価を当てると、LLMが約$0.0038、Rerankが$0.0020、合わせて約$0.006となる。Embeddingは入力がクエリ数十文字にとどまり、$0.00001未満で無視できる。

この内訳で重要なのは、Rerankがトークン量と無関係にクエリ1回あたり$0.002を占める点である。つまり費用はトークン量よりもチャットの回数に強く依存する。

## Decision

チャット1ターンを1回と数える回数制とし、1ユーザーあたり1日20回を上限とする。

残数はDynamoDBの同一テーブルへ`PK=USER#<userId>` / `SK=QUOTA#<JSTの日付>`のアイテムで持つ。ソートキーに日付を含めるため、日付が変わると別のアイテムになり、残数を戻す処理を持たない。過去分はTTLで自動的に消える。境界をJSTで切るのは、利用者の体感する「今日」と一致させるためである。

消費はchat-fnがグラフの実行前に行う。`used < 上限`を条件とする条件付きUpdateItemひとつで判定と加算を同時に済ませるため、同時にリクエストが届いても上限を超えて消費されることはない。上限に達している場合は429を返し、Bedrockを呼ばない。

グラフが途中で失敗しても消費分は戻さない。どこまでを失敗と見なすかの線引きが必要になり、返却処理そのものが新たな競合の原因になるためである。失敗の大半はすでにBedrockを呼んだ後に起きており、費用は発生している。

利用状況は`GET /api/users/{userId}/quota`で誰でも取得できる。チャット画面では本人の残り回数として、ユーザー画面では対象ユーザーの本日の利用回数として表示する。他ユーザーのプロフィール、チャット履歴、アップロード履歴はすでに全ユーザーへ公開しており、利用回数の公開はこの範囲を広げない。

## Consequences

メリット

- 月額費用の上限が「ユーザー数 × 20回 × 30日 × 約$0.006」で決まり、事前に見積もれる
- 判定と消費が1回の書き込みで完結し、競合状態を持たない
- 日付をキーに含めるため、リセットのためのバッチや定期実行を持たない
- 残数の判定に必要なデータがユーザーのパーティション内で完結し、既存のテーブル設計を変えない

デメリット・制約

- 回数はコストの代理指標であり、実際の消費量とは一致しない。長い質問と短い質問が同じ1回として扱われる
- リトライまで含めた最大ケースは1チャット約$0.014と試算しており、平均の2倍を超える。上限値は平均を根拠にしているため、全ユーザーが最大ケースを引き続けると想定を超える
- チャット1件につきDynamoDBの書き込みが1回増える
- 上限へ達した後は、その日は管理者を含めて誰も解除できない

見直し条件

- 上限値は`CHAT_DAILY_QUOTA`環境変数で変更する。1チャットあたりの利用量はchat-fnがチャットごとにログへ記録しており、実績から調整する
- 特定ユーザーだけ上限を変えたくなった場合は、Cognitoのグループを利用した個別上限を検討する

## Alternatives

### トークン数制

消費したトークン数で数える方式。実際の費用に最も近い。

しかし、1チャットのトークン数は最大7回のLLM呼び出しがすべて終わるまで確定しない。したがって判定は「開始前に残高を確認し、終了後に差し引く」形にならざるを得ず、残高が僅かなユーザーは1チャット分だけ超過できる。ストリームが中断した場合の計上も決める必要がある。

加えて、Rerankの費用はトークン量に依存しない。費用の3分の1をトークン数で説明できないため、精度の利点も限定的である。

### 継続的に補充するトークンバケット

一定時間ごとに残数を回復させる方式。突発的な利用を平準化できる。

しかし、最終補充時刻から現在までの経過時間で補充量を計算する必要があり、条件付きUpdateItemひとつでは表現できない。日付をキーに含める方式が持つ「リセット処理が存在しない」という利点も失われる。利用者にとっても、残数がいつ回復するかが日付境界より分かりにくい。

### CloudWatchの請求アラームによる事後検知

費用が閾値を超えたときに通知を受ける方式。実装を持たない。

しかし、検知した時点で費用はすでに発生しており、止めるには手作業が要る。上限を設けること自体が目的であるため、事後検知では要件を満たさない。
