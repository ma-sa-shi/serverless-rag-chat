# ADR-0017: チャット利用量のデイリークォータ導入方針

- Status: Accepted
- Date: 2026-08-30
- Updated: 2026-09-12

## Context

インフラは固定費がかからない構成にしているが、Bedrockの推論費用だけは利用量に比例して増え、上限がない。そのため、1人のユーザーがチャットを送り続けるだけで月額費用が見積もれなくなる。

API Gatewayのステージには20リクエスト/秒、バースト40のスロットリングを設定している。ただし、これは短時間に集中するリクエストを抑えるもので、累積の呼び出し回数は制限できない。

上限の単位を決めるため、6件のチャットで利用量を実測した。1チャットあたりの平均は以下の通りである。

- LLM: 入力5,514トークン、出力485トークン
- Embedding: 3.7回
- Rerank: 1回

ap-northeast-1のオンデマンド単価で計算すると、LLMが約$0.0038、Rerankが$0.0020で、合計は約$0.006になる。Embeddingは入力がクエリ数十文字と短く、$0.00001未満なので無視できる。

ここで注目すべきは、Rerankがトークン量に関係なく1回$0.002かかり、費用の約3分の1を占める点である。つまり、費用はトークン量よりもチャットの回数で決まる。

## Decision

チャット1ターンを1回と数える回数制にし、上限は1ユーザーあたり1日20回とする。

残数は、DynamoDBの既存テーブルに`PK=USER#<userId>` / `SK=QUOTA#<JSTの日付>`のアイテムとして持つ。ソートキーに日付が入っているので、日付が変われば別のアイテムになり、残数を戻す処理はいらない。古いアイテムはTTLで自動的に消える。日付の区切りをJSTにしているのは、利用者が感じる「今日」と合わせるためである。

消費はchat-fnがグラフを実行する前に行う。`used < 上限`を条件にした条件付きUpdateItemを1回呼ぶだけで判定と加算が済むため、リクエストが同時に届いても上限を超えて消費されることはない。上限に達していれば429を返し、Bedrockは呼ばない。

グラフが途中で失敗しても、消費した回数は戻さない。戻すにはどこまでを失敗とみなすかを決める必要があり、戻す処理そのものが新たな競合を生むためである。また、失敗の多くはBedrockを呼んだ後に起きており、その時点で費用はすでに発生している。

利用状況は`GET /api/users/{userId}/quota`で、どのユーザーのものでも取得できる。チャット画面には本人の残り回数を、ユーザー画面には対象ユーザーの本日の利用回数を表示する。他ユーザーのプロフィールやチャット履歴、アップロード履歴は元々全ユーザーに公開しているため、利用回数を公開しても公開範囲は広がらない。

## Consequences

メリット

- 月額費用の上限を「ユーザー数 × 20回 × 30日 × 約$0.006」で見積もれる。1ユーザーあたり月約$3.6になる
- 判定と消費が1回の書き込みで済み、競合が起きない
- 日付をキーに含めるので、リセット用のバッチや定期実行がいらない
- 判定に必要なデータがユーザーのパーティション内に収まり、既存のテーブル設計を変えずに済む

デメリット・制約

- 回数は費用の代わりに数える指標にすぎず、実際の消費量とは一致しない。長い質問も短い質問も同じ1回になる
- リトライを含めた最大ケースでは、LLMの呼び出しが7回、Rerankが2回になり、1チャット約$0.0137と試算している。これは平均の2倍を超える。上限値は平均をもとに決めているため、全ユーザーが最大ケースに当たり続けると見積もりを超える
- チャット1件ごとにDynamoDBへの書き込みが1回増える
- 上限に達すると、その日は管理者を含めて誰も解除できない

見直し条件

- 上限値は`CHAT_DAILY_QUOTA`環境変数で変える。chat-fnはチャットごとの利用量をログに記録しているので、その実績をもとに調整する
- 特定のユーザーだけ上限を変えたくなったら、Cognitoのグループを使った個別の上限を検討する

## Alternatives

### トークン数制

消費したトークン数で数える方式で、実際の費用に最も近い。

しかし、1チャットのトークン数は、最大7回のLLM呼び出しがすべて終わるまで確定しない。そのため、開始前に残高を確かめて終了後に差し引く形にするしかなく、残高がわずかなユーザーは1チャット分だけ上限を超えられてしまう。ストリームが途中で切れた場合にどう計上するかも決める必要がある。

さらに、費用の約3分の1を占めるRerankはトークン量に依存しない。トークン数で数えても費用を正確には表せず、精度の面での利点は限られる。

### 継続的に補充するトークンバケット

一定時間ごとに残数を回復させる方式で、突発的な利用を平準化できる。

しかし、補充量は最後に補充した時刻からの経過時間で計算する必要があり、条件付きUpdateItem 1回では書けない。日付をキーに含める方式の「リセット処理がいらない」という利点もなくなる。利用者から見ても、残数がいつ戻るのかが日付の区切りより分かりにくい。

### CloudWatchの請求アラームによる事後検知

費用が閾値を超えたときに通知を受け取る方式で、実装がいらない。

しかし、通知が届いた時点で費用はすでに発生しており、止めるには手作業が必要になる。目的は費用に上限を設けることなので、事後に検知するだけでは要件を満たさない。
