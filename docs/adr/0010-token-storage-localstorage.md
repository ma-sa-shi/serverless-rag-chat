# ADR-0010: トークンをlocalStorageへ保存する

- Status: Superseded by [ADR-0018](./0018-token-storage-httponly-cookie.md)
- Date: 2026-07-19

## Context

CognitoのAuthorization Code + PKCEフローにより、SPAはアクセストークンとリフレッシュトークンを受け取る。このトークンをブラウザのどこへ保存するかが課題である。

保存先はXSS発生時の被害範囲と、リロードや複数タブでのセッション維持に直結する。本システムはチャット詳細やドキュメントを別タブで開く利用を想定しており、タブを跨いでセッションが切れない必要がある。

## Decision

トークンをlocalStorageへ保存する。`oidc-client-ts`の`WebStorageStateStore`に`window.localStorage`を指定する。

採用理由は次の3点である。

- リロードと複数タブでセッションを維持できる
- リフレッシュトークンがタブを閉じても保持されるため、トークン更新をrefresh token grantで行える。iframeによるサイレントサインインに依存せず、サードパーティCookieをブラウザがブロックする影響を受けない
- バックエンドに認証用エンドポイントを持たず、JWT検証のみという責務の範囲に収まる

XSSによるトークン窃取のリスクは受容した上で、次の対策で影響を低減する。

- Reactのデフォルトエスケープを利用する
- サードパーティスクリプトを導入しない
- アクセストークンの有効期限を1時間とし、漏えい時の影響範囲を限定する
- CloudFrontのレスポンスヘッダーでContent Security Policyを設定する

## Consequences

メリット

- 複数タブとリロードでサインイン状態が維持され、再認証の頻度が下がる
- 認可コードの交換やCSRF対策を自前で実装せずに済む

デメリット・制約

- XSSが発生した場合、トークンを窃取される。HttpOnly Cookieであれば防げる攻撃を防げない

見直し条件

- XSSによるトークン窃取の影響を受容できなくなった場合はHttpOnly Cookieを用いるBFF方式へ見直す

## Alternatives

### sessionStorage

タブ単位のスコープであり、新しいタブを開くたびに再認証が走る。そのため、本システムの複数タブ利用と相性が悪い。XSSに対する耐性はlocalStorageと実質同等で、リスクを下げる効果もないため不採用とした。

### メモリ保持とサイレント更新

XSSでの窃取リスクは最も低い。しかしリロードのたびにトークンが失われ、Hosted UIへのリダイレクトが発生する。iframeによるサイレントサインインで回避する手段はあるが、サードパーティCookieのブロックを受けるうえ、UXの劣化も大きいため不採用とした。

### HttpOnly Cookieによるトークン保管とBFF

JavaScriptからトークンへアクセスできないため、XSSに対して最も堅牢である。しかし認可コードとトークンの交換をSPAからバックエンドへ移し、Cookieの発行、CSRF対策、トークン更新とサインアウトのエンドポイントを自前で実装する必要がある。`oidc-client-ts`が担っている処理をバックエンドへ書き直すことになり、ADR-0004の責務範囲も広がる。社内利用に対して、増える実装量が見合わないため不採用とした。
