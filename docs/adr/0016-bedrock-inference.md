# ADR-0016: 推論の呼び出し経路をAmazon Bedrockへ統一する

- Status: Accepted
- Date: 2026-08-30

## Context

これまでは、回答生成にOpenAI、埋め込みとリランクにCohereのAPIを直接呼んでいた。この構成には2つの課題がある。

- APIキーの管理が必要になる。SSM Parameter StoreのSecureStringで2本のキーを保管しているが、自動ローテーションの手段がなく、更新は手作業になる
- 社内文書の本文が外部のSaaSへ出る。取込時の埋め込み、検索時のリランク、回答生成のいずれでも、チャンクの本文をOpenAIまたはCohereへ送っている

一方で、Bedrockで使えるモデルが増え、Cohere Embed v4とCohere Rerank 3.5がap-northeast-1のオンデマンド推論で使えるようになった。ただし、リランクはRerank 3.5までで、これまで使っていたrerank-v4.0-fastに相当するモデルはない。

## Decision

推論の呼び出し経路をすべてBedrockへ統一する。呼び出し先のエンドポイントは、証明書用を除く他のスタックと同じap-northeast-1とする。採用するモデルはarchitecture.md 7.2に示す。

APIキーは廃止する。SSM SecureStringの2つのパラメータとKMSによる復号をやめ、Lambdaの実行ロールにBedrockの呼び出し権限を与える。これにより、認可はIAMに一本化される。

4つのチェーンはすべて同じモデルで賄う。ただし、回答生成と補助処理の設定は分けたまま残し、回答生成だけを差し替えられるようにする。クエリ生成と自己評価は構造化出力を使うため、補助処理にはJSON Schemaの件数制約を守れるモデルを選ぶ。この条件はモデルを差し替えても変わらない。

モデルを1つにそろえるのは、監視と設定の対象を増やさないためである。対抗馬としたgpt-oss-120bは、回答生成に限れば、複数の処理をまとめて説明する質問でより正確に答えた事例が1問あった。しかし、構造化出力の件数制約を守れず、6回試行して6回とも上限を超えたため、補助処理には使えない。採用するなら2モデル構成にするしかない。さらに、gpt-oss-120bのクォータはService Quotasに公開されておらず、上限の確認も引き上げの申請もできない。リランクで毎分3リクエストという上限をすでに抱えている状況で、上限すら確認できないモデルを併用する負担は、1問で見えた品質差より重いと判断した。

埋め込みはモデルも出力次元も変わらないため、取込済みドキュメントの再取込はいらない。デプロイ済みのインデックスで実際に検索し、Cohereの直接APIで登録したベクトルがBedrock経由のクエリで正しくヒットすることを確認した。

採用理由は次の2点である。

- キーの保管とローテーションが不要になる。キーそのものがなくなるため、手作業での更新も残らない
- 文書の本文と検索クエリが第三者のSaaSへ渡らなくなる

データを処理するリージョンには要件を設けない。採用したモデルはいずれも結果として国内で処理されるが、これは選定の結果であって制約ではない。

## Consequences

メリット

- APIキーの保管とローテーションが不要になり、認可がIAMに一本化される
- 文書の本文と検索クエリがAWSの外へ出ない
- 認証情報の扱いがboto3にそろい、ingest-fnがhttpxでCohereのREST APIを直接呼ぶ実装がなくなる

デメリット・制約

- リランクがRerank 3.5へ後退する。第三者のベンチマークでは、Rerank 4 Fastとの差が総合で54 ELO、ビジネス系のデータセットで約300 ELOと報告されている。社内文書はこの差が出やすい領域にあたるが、自前のデータでは測定していない
- スループットがアカウントのクォータに縛られる。AWSの既定値はCohere Embed v4が毎分1,000リクエスト、Cohere Rerank 3.5が毎分250リクエストだが、現在のアカウントにはそれぞれ毎分10と3が適用されている。1チャットでリランクを1回、埋め込みをクエリ数だけ呼び、最大1回の再試行でそれぞれ倍になる。そのため、この水準では同時アクセスが重なるとスロットリングされる。取込側も同じ埋め込みのクォータを共有し、96チャンクずつ逐次に呼ぶため、大きな文書1件でも上限を超えうる
- このクォータの制約はBedrockではなくアカウントの状態によるもので、適用値が既定値まで戻れば解消する。ただし、Service Quotasからは引き上げを申請できない
- 使えるモデルが、Bedrockの提供状況とアカウントの開放状況に左右される。第一候補としたGPT-5.6 Lunaは、モデル契約を終えても、どの経路で呼んでもaccess_deniedが返る。mantleエンドポイントにはクォータが割り当てられているため、上限ではなくその手前で拒否されている。原因はAWSに問い合わせている
- 構造化出力はConverse APIのツール呼び出しを経由するため、OpenAIのStructured Outputsとは挙動が異なる

見直し条件

- GPT-5.6 Lunaを呼び出せるようになった時点で、回答生成の品質を比較して差し替えを判断する。差し替える場合はglobalの推論プロファイル経由になり、処理するリージョンが国内に限られなくなる
- BedrockがCohere Rerank 4に対応した時点で乗り換える
- クォータの適用値が既定値まで戻れば、スループットの制約はなくなる。それまでにスロットリングが目立つようになった場合は、Multi Queryのクエリ数を減らす

APIキーの保管方式を定めたADR-0008は、対象となるキーがなくなるため本ADRで置き換える。

## Alternatives

### リランクのみCohereのAPIを直接呼ぶ

Rerank 4 Fastの品質と、毎分3リクエストより高いレート上限を保てる。

しかし、Cohereのキーが1本残るため、キー管理の廃止と、本文をAWS内に留めるという2つの狙いがどちらも果たせなくなる。リランクは検索したチャンクの本文をそのまま送る処理であり、ここが残る限りデータの所在を説明できない。移行の目的を打ち消すため、採用しない。

### 現状維持

OpenAIとCohereを直接呼び続ければ、移行の作業も、リランクの品質低下やレート上限の低下も避けられる。

しかし、キーの手作業での管理と本文の外部送信という2つの課題がどちらも残るため、採用しない。
