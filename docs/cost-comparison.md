# サーバーレス構成の損益分岐点 — 移植元アプリ(ECS)との比較

本アプリは、コスト最適化を目的として従来の ECS 構成から Lambda を活用したサーバーレス構成へ移行した。以下に、本アプリと移植元アプリのインフラ構成を示す。

| | 構成 |
|---|---|
| 本アプリ | Lambda(api-fn / chat-fn / ingest-fn), API Gateway, DynamoDB, S3 Vectors。（※VPC不使用） |
| 移植元アプリ | ECS Fargate Spot 2タスク(FastAPI / Next.js、各0.25vCPU・0.5GB、平日9時から19時稼働)RDS MySQL(db.t4g.micro), Chroma on EFS |

本ドキュメントでは、両構成におけるコストの損益分岐点およびその算定根拠について解説する。

## 1. 結論

月間の合計ストリーミング時間が 722 時間を下回る場合、本アプリのコストは移植元アプリを下回る。1 チャット当たりの処理時間を 30 秒と仮定した場合、これは月間約 86,600 チャットに相当する。

![月間ストリーミング時間に対する両構成の月額費用。722時間で交差する](./diagrams/cost-comparison.svg)

移植元アプリのコストは FastAPI のタスク数増加に応じて段階的に増加するのに対し、本アプリのコストは月間ストリーミング時間に比例して直線的に増加する。

なお、移植元アプリはベクトルデータベースとしてファイル形式の Chroma を採用しており、FastAPI を複数タスクへ拡張する際は同時書き込みの競合が発生する。そのため、FastAPI が 2 タスク以上となる場合は Chroma をサーバーモードへ移行する必要があり、本比較における移植元アプリの試算にはその移行コストも含めている。

## 2. 費用モデル

両システムの費用モデルを以下に定義する。なお、本モデルでは全体コストに与える影響が大きい支配的な要素（支配項）のみを抽出して算出している。

### 2.1 本アプリ(Lambda版)

$$A(N) = (c \cdot T + m) \cdot N + s + l \cdot N$$

- $c$ … chat-fn のインフラ実行時間単価。$1.33334 \times 10^{-5}$ / GB秒（arm64）にメモリ 1.0 GB（1,024 MB）を乗じた $1.33334 \times 10^{-5}$ / 秒
- $T$ … 1チャット当たりのストリーミング時間（30 秒と仮定）
- $m$ … 1 チャット当たりに発生する API Gateway および api-fn の処理費用（$1.6 \times 10^{-5}$）
- $s$ … 本アプリの固定ストレージ費用（約 \$0.4 / 月）
- $N$ … 月間チャット数
- $l$ … 1チャット当たりの外部API費用

【$T$（30 秒）の設定根拠】
本番環境における実測値に基づき算出している。chat-fn の実行ログ（8 回分）によると、ストリーム出力時間は 6.5 秒〜 20.1 秒（平均 12.1 秒）であったのに対し、課金対象となる実行時間（Billed Duration）は 6.5 秒〜 32.2 秒（平均 21.1 秒）であった。この差分はコールドスタートに起因する。8 回中 6 回でコールドスタートが発生し、そのうち 4 回ではコンテナイメージの初期化処理が上限（10 秒）に達したため、超過分が Invoke 側の Duration に計上された。アクセス頻度が低い環境では大半のリクエストがこの経路を辿るため、T には平均ストリーム時間ではなく、平均 Billed Duration を上回る 30 秒を採用している。

【$m$（$1.6 \times 10^{-5}$）の設定根拠】
1 チャットにつき API Gateway へのリクエストが 3 件（SSE 通信 1 件、チャット一覧・詳細取得 2 件）発生し、そのうち api-fn が処理する 2 件を「メモリ 512 MB、実行時間 200 ms」と仮定して算出した。リクエスト課金と api-fn の実行時間を合算すると $1.6 \times 10^{-5}$ となる。

### 2.2 移植元アプリ(ECS版)

$$B(N) = F(n) + l \cdot N$$

- $F(n)$ … FastAPI のタスク数を $n$ 台にした場合の月額インフラ費用

$F(n)$ の内訳は以下の通りである。

$$\begin{aligned} F(n) &= 22.91 + 2.088 \times (1 + n) + 3.09 \quad (n \ge 2) \\ F(1) &= 22.91 + 2.088 \times 2 \quad (n = 1) \end{aligned}$$

固定費 \$22.91 / 月 は負荷状況にかかわらず発生し、その内訳は以下の通りである。

| 構成要素 | 月額費用 |
|---|---:|
| RDS db.t4g.micro（\$0.025 × 730時間） | \$18.25 |
| RDS gp2ストレージ(20GB) | \$2.76 |
| EFS | \$1.00 |
| その他固定費(Secrets Manager、ECR、ログ) | \$0.90 |
| 合計 | \$22.91 |

$n \ge 2$ の場合にのみ加算される \$3.09 / 月 は、Chroma をサーバーモードで稼働させるための専用タスク（0.5 vCPU / 1 GB）およびパブリック IPv4 アドレスの利用コストである。

タスク増設時の単位費用 \$2.088 / 月 は、ECS タスクを追加した際の実質的なリソース増加分を表す。チャット処理を担う FastAPI タスクを追加する一方、SSE 通信をプロキシする Next.js タスクは 1 台のまま維持できる想定としている。

| 増設ユニット（1タスク分） | 月額費用 |
|---|---:|
| Fargate Spot 1タスク（0.25 vCPU・0.5 GB / 月間217時間稼働） | \$1.003 |
| パブリック IPv4 アドレス 1 個（217時間分） | \$1.085 |
| 合計 | \$2.088 |

各タスク数 $n$ における $F(n)$ の値は以下の通りである。

| タスク数 n | 構成内容 | 月額インフラ費用 $F(n)$ |
|---:|---|---:|
| 1 | 現行構成(FastAPI 1台 + Next.js 1台) | \$27.09 |
| 2 | FastAPI 2台 + Chromaサーバー | \$32.26 |
| 3 | FastAPI 3台 + Chromaサーバー | \$34.35 |
| 4 | FastAPI 4台 + Chromaサーバー | \$36.44 |

### 2.3 タスク数とストリーミング時間の関係

月間ストリーミング時間 $S$（時間/月）は、月間チャット数 $N$ および 1 チャット当たりのストリーミング時間 $T$（秒）から $S = N \times T \div 3600$ と定義される。$T = 30$ 秒の場合、$N = 120 \times S$ と換算できる。

$F(n)$ のタスク数 $n$ は、この $S$ によって決定される。FastAPI の 1 タスクが同時に処理できるストリームを 1 本と仮定した場合、1 タスクが 1 か月に処理可能な上限量は月間稼働時間と同じ 217 時間となり、必要なタスク数は以下のように求められる。

$$n = \lceil S / 217 \rceil$$

なお、この仮定を緩和した場合の影響範囲については「3. 前提条件と検証」に詳述する。

### 2.4 変数および単価設定

損益分岐点が月間ストリーミング時間 $S$ の単一変数で決定される理由は以下の 2 点である。

1. $A(N) = B(N)$ の方程式を解く際、両辺に含まれる外部 API 費用 $l \cdot N$ が相殺されるため、分岐点はインフラ費用のみに依存する。
2. $T$ を 30 秒に固定することで $N$ と $S$ を相互変換でき、移植元アプリに必要なタスク数 $n$ も $S$ から一義的に定まるため。

以下に適用した単価（東京リージョン）を示す。値は AWS Price List API の地域別インデックスより取得した（取得日：2026年8月18日、末尾 2 行のみ 2026年8月21日）。

| 項目 | 単価（東京リージョン） |
|---|---|
| Lambda 実行時間(arm64) | \$0.0000133334/GB秒 |
| Fargate(x86) | \$0.05056/vCPU時間 + \$0.00553/GB時間 |
| パブリックIPv4アドレス | \$0.005/時間 |
| RDS db.t4g.micro(MySQL、Single-AZ) | \$0.025/時間 |
| RDS gp2ストレージ | \$0.138/GB月 |
| API Gateway REST APIリクエスト | \$4.25/100万リクエスト |
| Lambda リクエスト | \$0.20/100万リクエスト |

※ Fargate Spot の価格は市場状況により変動し Price List API に含まれないため、オンデマンド料金の 70% 割引と仮定して計算している。また、EFS および Secrets Manager は全体コストに対する影響が極めて小さいため、移植元アプリの実実績値をそのまま適用している。

### 2.5 損益分岐点の導出

$A(N) = B(N)$ を $S$ について解く。$T = 30$ 秒のとき $N = 120 \times S$ となるため、本アプリのインフラ実行コストは 1 時間当たり $(c \cdot T + m) \times 120 = \$0.04992 / 時間$ と算出される。

$$0.04992 \times S + 0.4 = F(n)$$

移植元アプリのコストは $n = \lceil S / 217 \rceil$ に応じて階段状に増加するため、$S$ の範囲ごとに $F(n)$ を適用して交点を特定する。分析の結果、交点は $n = 4$（$F(4) = \$36.44$）の帯域に存在する。

$$S = (36.44 - 0.4) \div 0.04992 = 721.9$$

したがって、損益分岐点は月間 722 時間（$T = 30$ 秒換算で月間約 86,600 チャット）となる。これは、移植元アプリが現行構成（1 タスク）で処理できる上限（217 時間）の約 3.3 倍に相当する。

### 2.6 費用モデルにおいて除外した項目

本モデルでは、算出を簡略化するため以下の非支配的な項目を除外している。

- ingest-fn の実行時間およびリクエスト課金（ドキュメント取込処理はチャット数と直接比例しないため）
- DynamoDB、S3、S3 Vectors、ECR へのデータ読み書き課金
- 無料枠の範囲内に収まる各種サービス費用（SQS、CloudWatch、X-Ray、SNS、CloudFront、Cognito）
- 移植元アプリにおける ECR、CloudWatch Logs、RDS バックアップストレージ、EFS スループット課金、およびデータ転送量課金

※ Lambda の無料枠（400,000 GB秒/月）は本来無視できない規模であるが、適用条件が AWS アカウントの利用状況に依存するため、本モデルでは考慮していない。

## 3. 前提条件と感度分析

**「FastAPI 1 タスクが同時に処理するストリームは 1 本」という仮定**
非同期処理が可能な FastAPI は LLM からのレスポンス待ち時間に他のリクエストを並行処理できるため、この仮定は移植元アプリ側に不利（高く見積もる側）に作用する。しかし、1 タスクが同時に $k$ 本を処理できると仮定した場合でも、削減されるのは必要タスク数 $\lceil S / (217k) \rceil$ のみであり、移植元アプリの費用が固定費を含む $F(1) = \$27.09$ を下回ることはない。したがって、理論上の分岐点の下限は $(27.09 - 0.4) \div 0.04992 = 535 \text{時間/月}$ となり、同時実行数の仮定にかかわらず分岐点は 535 時間〜 722 時間の範囲内に収まる。

**$T = 30$ 秒という固定値の妥当性**
1 時間当たりの処理チャット数は $T$ に依存するため、$T$ が短くなるほど固定費用 $m$ の比重が高まり分岐点は低下する。実測平均（ストリーム時間）に近い $T = 12$ 秒で試算した場合、分岐点は 683 時間となる。逆に $T$ が長くなるほど $m$ の影響度は下がり、分岐点は 751 時間へ漸近する。

**トラフィックが稼働時間内で均等に分散するという仮定**
移植元アプリに必要な同時実行数は実際のアクセス分布に依存する。アクセス集中が存在する場合はより多くのタスクが必要となるため、この仮定は移植元アプリ側を安く見積もる側に作用している。

**Fargate Spot の割引率仮定**
本試算ではオンデマンド料金の 70% 割引と仮定している。割引率が 50% であった場合、$F(n)$ の月額は約 \$4.7 上昇し、損益分岐点は約 13% 増加する。

**単価の取得時点**
適用した単価は AWS Price List API の地域別インデックス(`https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/<サービス>/current/ap-northeast-1/index.json`)より取得した時点の値に基づいている。
