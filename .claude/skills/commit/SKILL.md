---

## コミットメッセージ

- 件名・本文とも英語で書く
- 件名は `type(scope): 要約` とし、命令形で72文字以内に収める
- typeは `feat` / `fix` / `docs` / `refactor` / `test` / `build` / `ci` / `chore`
- scopeは `frontend` / `backend` / `cdk` / `ci` / `auth` / `adr`。複数はカンマで繋ぎ、全体に及ぶ場合は省く
- 本文は必要な場合だけ書く。1文で何が変わったかを述べ、変更ごとに1つの箇条書きで「なぜ」と重要な設計判断を補う。実装手順や調査メモは書かない

## プルリクエスト

- タイトルは英語の命令形で、`type(scope):` は付けない。本文は日本語で書く
- 本文は次の `###` 見出しで構成し、見出しの追加・改名はしない
  1. 実装内容（必須）
  2. 検証結果（任意）
  3. 注意事項（任意）
- 末尾に区切り線 `---` を置き、含まれるコミットの件名を並べ、`Closes #<番号>` で締める

本文には差分から読み取れないことだけを書く。

- 実装内容は、変更したモジュールごとに何がどう変わったかを1行ずつ書いて止める
- レビューで判断が必要な設計上の選択と、代替案を却下した理由は明示する
- 検証結果には実行したコマンドと確認した事実を書く。`make test`が通っただけなら実装内容の末尾に1文で足し、見出しは立てない
- 注意事項には運用手順の変更、誤解されやすい点、積み残しを挙げる
- 調査や試行錯誤の経緯、コミットメッセージと同じ内容は書かない
